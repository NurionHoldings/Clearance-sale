# 다판다 입점 전자계약·내부 정산 운영

## 구현 범위

`/operations.html`은 로그인한 업체와 `dapanda-admin` 역할을 가진 관리자를 위한 별도 운영 화면이다.
시제품 상품 카탈로그·장바구니와 분리되어 있으며 실제 PG 결제·은행 송금은 실행하지 않는다.

- 업체 정보 서버 저장·수정, 변경 시 검증 해제. 업체당 계정 1개, 전체 최대 100개.
- 관리자 사업자·서명 대리권·지급계좌 명의 대조 기록. 계좌번호 자체 대신 별도 금융 업무에서 확인한 계좌의 사내 검증참조번호를 기록한다.
- 계약별 플랫폼 수수료율·배송비 기준·부가세 포함/별도·PG 실비/비율/플랫폼 부담·환불 시 PG 수수료 반환 정책·기간·정산 주기·대기일·특약 지정.
- 관리자 원문 미리보기 → 같은 해시의 문서 제공자 서명·발행 → 업체 본문 확인 → 업체 전자서명.
- 문서·서명 계정·이메일·서명시각·열람 확인·원문 및 서명본 SHA-256 보관. 미서명 발행 철회, 체결 후 원문 수정 API 없음. 변경은 새 버전 재체결.
- HTML 열람·저장, 브라우저 인쇄/PDF 저장, 원문·서명기록 JSON 저장.
- PG/입금 증빙 파일 보관과 매출·환불 사건 등록 → 관리자의 실제 증빙 대조 → 정산 산출.
- 아르카온 규칙 엔진 재계산·검증·보류 사유·수정 제안 → 관리자 승인 → 내부 지급요청서 작성.
- AI Gateway 모델이 설정되면 규칙 검증 결과에 대한 LLM 수정 제안을 추가 저장. LLM에는 질문·합계·차단 사유만 전송하며 업체명·계좌·증빙은 전송하지 않는다.
- 정산·지급요청 근거 JSON 저장과 정산서 인쇄/PDF 저장. 계정별 자료 접근 차단, 쓰기 요청 Origin 검사, 감사 이력 해시 연결 검증.

## 초기 설정

1. Netlify는 `npm run build`, publish `dist`로 배포한다. 서버 소스·DB 마이그레이션·테스트는 정적 파일에 포함하지 않는다.
2. `@netlify/database`와 커밋된 마이그레이션으로 DB를 배포 시 구성한다. 직접 운영 SQL을 실행하지 않는다.
3. Netlify 프로젝트 `clearlancesale` → Identity를 활성화하고 업체 가입 방식(초대 전용 또는 이메일 인증 가입)을 선택한다. 자동 이메일 인증 생략은 사용하지 않는 것을 권장한다.
4. 운영자 계정 생성·이메일 인증 후 Identity에서 `app_metadata.roles`에 `dapanda-admin`을 지정한다. 역할은 다음 로그인 또는 토큰 갱신부터 반영된다. 일반 업체는 이 역할이 없어야 한다.
5. 초대·인증·비밀번호 복구 링크는 루트와 운영센터에서 처리한다. Identity는 로컬 서버에서 실제 인증을 제공하지 않으므로 배포 환경에서 확인한다.
6. LLM 검토를 사용할 때는 지원 모델을 Netlify AI Gateway 제공 모델 목록에서 확인하고 Functions 범위 환경변수 `ARKAON_REVIEW_MODEL`에 지정한다. 공식 OpenAI SDK는 주입된 공급자 인증정보를 사용한다. 미설정 시 규칙 엔진은 사용 가능하며 LLM 검토는 미연결 상태로 표시한다.

관리자 권한 부여·가입 정책·모델 설정에는 실제 운영자 계정 및 대시보드 설정이 필요하다. 코드 배포만으로 계정이 생성되거나 역할이 부여되지는 않는다.

## 계산·검증 기준

원화 정수와 BigInt 비율 계산을 사용한다. 사건별 1원 반올림 방식을 계약 본문에 명시하고 공급가·수수료 부가세·PG 총액을 나눈다. 상품 과세유형이나 법정 세금계산서를 자동 판정하지 않는다.

- PG 실비는 증빙상 부가세 포함 총액이다. 환급은 환불 사건의 음수 PG 수수료로 기록한다.
- 환불은 같은 계약의 검증된 원매출에 연결한다. 누적 총액·배송비가 원거래를 초과할 수 없다.
- 별도 고유번호와 증빙으로 새 환불을 추가한다. 이미 정산된 매출·계약 원본을 덮어쓰지 않는다.
- 지급 전 추가 환불이 접수되면 다른 초안이 점유 중이어도 기존 정산서의 지급요청을 보류한다.
- 거래는 정산서 하나만 점유한다. 취소 시 거래 점유만 해제하며 취소된 정산 스냅샷·감사 이력은 남긴다.
- 음수·0원 정산은 지급요청을 만들지 않는다. 취소 후 차기 매출과 합산해 미정산 환불을 포함한다.
- 정산 검토·승인·지급요청 시 서명 계약·원증빙·업체 검증 버전·재계산을 다시 대조한다.
- 지급요청은 정산서당 한 건만 작성된다. 실제 이체·은행 접수·지급완료 API는 없다.

## 전자서명·계약 유의 범위

전자서명 방식은 인증된 이메일 계정 + 성명 입력 + 명시적 동의 + 대리권 확인이다.
계정 인증이 법인 대표권·실명 인증을 자동 입증하지 않으므로 관리자가 관련 서류를 대조해야 한다.
외부 인증사업자, 공인 타임스탬프, 인증서 기반 서명은 연동하지 않았으며 그 서비스를 사용했다고 표시하지 않는다.
서명 계약의 법률·세무 적합성을 AI가 보증하거나 자동 승인하지 않는다. 계약 문안·구조 조건·특약은 발행 담당자가 확인한다.

근거 확인: 국가법령정보센터 전자서명법 제3조 및 전자문서 및 전자거래 기본법 제4조의2·제5조(2026-11-01 확인).

## 검증 명령·범위

`npm run test:operations`, `npm run check`, `npm run build`.
브라우저 통합 검증: `node tests/operations/browser.mjs` (Playwright 설치 경로는 실행 환경에 맞게 지정).
실제 SQL 호환 테스트 DB로 업체 검증·계약 미리보기·양측 서명·증빙·정산·지급요청까지 실행하고, 브라우저에서는 Identity SDK만 테스트 대체 모듈을 사용한다.
실제 운영자·업체 계정의 인증/메일 및 실제 PG·은행 자료 대조는 이 테스트로 검증했다고 주장하지 않는다.

## 실제 운영 전 남는 연결

실제 운영자 역할·업체 계정, 선택한 AI 모델의 연결 확인, 실제 PG 거래 수집·웹훅 검증, 은행 이체·계좌등록 시스템 연동, 문서 보존기간·삭제 운영 정책이 별도로 필요하다.
이 구현은 내부 계약·증빙 정산·지급요청의 서버 기능이며, 주문·결제·정산·실제 이체 전체가 자동 운영된다고 표시하지 않는다.
